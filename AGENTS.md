## Confirmed repository architecture

- `HomeServeIT.slnx` contains the ASP.NET Core web project and `HomeServeIT.Web.Tests`, an xUnit regression project.
- The project targets `net10.0` and uses ASP.NET Core MVC with Razor views, Razor Pages for Identity, nullable reference types, and implicit usings.
- Role-specific MVC code is divided into `Areas/Admin`, `Areas/Customer`, and `Areas/Technician`. Role names come from `HomeServeIT.Web/Constants/Roles.cs`: `Administrator`, `Customer`, and `Technician`.
- `ApplicationDbContext` extends `IdentityDbContext<ApplicationUser>`. EF Core uses Pomelo's MySQL provider and reads `ConnectionStrings:DefaultConnection`.
- Schema history is in `HomeServeIT.Web/Migrations`. Development startup applies migrations and creates missing roles; non-Development startup never mutates the schema. `--initialize-database` is the explicit deployment/maintenance path. Disposable Development fixtures require the reset command documented in `docs/phase-5-7-verification.md`. The guarded `TestData:UseCurrentModel` fixture option uses `EnsureCreated` and is not migration verification.
- ASP.NET Core Identity handles accounts, roles, cookies, and lockout rules. Do not replace it with custom authentication.
- SignalR is enabled through `ChatHub` and mapped at `/chathub`.
- Administrator-managed application settings are stored in the singleton `ApplicationSettings` row, with field-name-only changes recorded in `ApplicationSettingAudits`. `ApplicationSettingsService` is the only application service that should update them.
- Tailwind CSS 3 scans Razor and JavaScript files. `wwwroot/css/site.css` is the source and ignored `wwwroot/css/app.css` is generated by the MSBuild `Tailwind` target before each build.
- Playwright browser smoke, workflow, responsive, keyboard, and axe accessibility tests live in `HomeServeIT.Web/tests/browser`. The isolated phase runner exercises Chromium and desktop WebKit; the ordinary configuration also defines Firefox and mobile WebKit.
- `ScreenshotBot/`, when present, is a separate Puppeteer-based local screenshot utility. It is not part of the .NET solution, is not an automated test suite, and has no npm task wiring. Its scripts expect the HTTP launch profile at `http://localhost:5160`.

Do not casually change framework or package major versions. In particular, the app targets .NET 10 while its Microsoft EF Core/Identity and Pomelo package references are currently version 9.x. Treat upgrades as a dedicated task that includes compatibility research, migration review, and runtime verification.

## Setup and verified commands

Run solution commands from the repository root unless a command explicitly changes directory.

```bash
# Install the web project's Tailwind dependencies.
cd HomeServeIT.Web
npm install
npx playwright install
cd ..

# Restore and build the current solution.
dotnet restore HomeServeIT.slnx
dotnet build HomeServeIT.slnx --no-restore
dotnet test HomeServeIT.slnx --no-restore

# Run with the checked-in Development HTTP profile on localhost:5160.
dotnet run --project HomeServeIT.Web --launch-profile http

# Use hot reload during interactive development.
dotnet watch --project HomeServeIT.Web --launch-profile http
```

The build already runs this checked-in Tailwind command from the web project directory:

```bash
npx tailwindcss -i ./wwwroot/css/site.css -o ./wwwroot/css/app.css
```

There is no checked-in npm `build` or Tailwind `watch` script. Do not claim one exists or invoke `npm run build`/`npm run watch` unless a task adds and verifies those scripts. Edit `site.css`, Razor classes, or JavaScript inputs rather than the generated `app.css`.

Run the Playwright browser suite from the web project. It starts the HTTP Development app unless `HOMESERVE_BASE_URL` points to an already-running safe test target. The authenticated administrator smoke test skips unless its credentials are supplied through environment variables.

```bash
cd HomeServeIT.Web
npm test

# Optional authenticated coverage: export HOMESERVE_ADMIN_EMAIL and
# HOMESERVE_ADMIN_PASSWORD from a secret store before running npm test.
```

For EF Core schema changes, use the web project as both target and startup project:

```bash
dotnet ef migrations add <DescriptiveMigrationName> --project HomeServeIT.Web --startup-project HomeServeIT.Web
dotnet ef database update --project HomeServeIT.Web --startup-project HomeServeIT.Web
```

Generate migrations with the EF tool; do not hand-create or partially edit a migration, designer, or model snapshot. Review generated operations and the snapshot before accepting them. Database update and application startup are state-changing operations: first confirm that `DefaultConnection` resolves to an expendable development database, then obtain any approval required by the task. Never run them against an unknown, shared, staging, or production database merely to validate code.

If `ScreenshotBot/` is in scope, install its dependencies in that directory and run scripts directly because its `package.json` has no capture scripts:

```bash
cd ScreenshotBot
npm install
node take_screenshots.js
# Authenticated coverage, only when the local Development seed data is appropriate:
node take_screenshots_auth.js
```

Do not publish screenshots containing customer data or authenticated content. Do not treat a successful screenshot capture as functional coverage.

## Code organization and conventions

- Follow the style of the file being changed; the repository contains both file-scoped namespaces and brace-scoped namespaces. Avoid broad style-only rewrites.
- Keep area-specific controllers, models/ViewModels, views, and partials in the matching Area. Controllers must retain the correct `[Area]` and role-based `[Authorize]` boundary.
- Keep controllers responsible for HTTP concerns and orchestration. Move reusable or multi-step business logic into focused services and register non-static services with the appropriate lifetime in `Program.cs`. `ApplicationDbContext`-dependent services should normally be scoped.
- Use dedicated input models/ViewModels for nontrivial form or API input. Validate `ModelState` and business rules server-side. Do not bind writable entity types when that exposes fields the caller must not control.
- Keep Razor views focused on rendering. Reuse existing layouts and partials, preserve tag helpers and validation summaries, and avoid embedding database or authorization logic in views.
- Use asynchronous EF Core APIs in request and hub paths. Shape queries deliberately with `Where`, `Select`, `Include`, and `AsNoTracking` for read-only work; avoid loading entire tables or introducing N+1 queries.
- Use UTC for persisted timestamps, matching the existing models and services. Convert only at display or explicit boundary layers.
- Preserve existing global query-filter behavior: cancelled service requests must not leak financial artifacts into active billing, quotation, notification, dashboard, or reporting views. Use `IgnoreQueryFilters` only when the operation intentionally handles hidden records.
- For a schema change, update the model/configuration, create one descriptive migration, and inspect MySQL compatibility and data-loss risk. Do not rewrite previously applied migrations without explicit authorization.
- State-changing MVC form actions must be POST (or another appropriate non-GET verb) and use antiforgery validation. PRG redirects are the existing MVC pattern.
- Use constants for roles. Do not trust the denormalized `ApplicationUser.Role` string as the authorization source; use Identity roles and `UserManager`/claims.
- SignalR methods must authenticate and authorize every request-specific action. Validate request IDs, group membership, message inputs, and ownership/assignment on the server before reading, persisting, or broadcasting data.

## HomeServe business invariants

Treat the following as server-side invariants, including for direct API calls, forged form posts, concurrent requests, and hub invocations. UI visibility is never authorization.

- Enforce strict Administrator, Customer, and Technician separation. A generic `[Authorize]` is insufficient for an operation limited to a role or resource owner.
- A Customer may read or mutate only the `Customer` record tied to the current Identity user and that customer's requests, devices, invoices, quotations, messages, deliverables, and support records.
- A Technician may read or mutate only active requests assigned to the `Technician` record tied to the current Identity user. Re-check assignment and customer archival/cancellation state on every action.
- Administrators may perform only explicitly permitted administrative workflows. Sensitive operations still need record-state checks and an auditable actor/action/time/result trail.
- Validate both the current and target state for every service-request transition. Status strings currently appear across controllers, views, notifications, filters, and reports; when adding or renaming one, locate and update every consumer. Do not allow arbitrary transitions merely because a target value appears in an allowed-values array.
- Preserve workflow gates: work must not start or complete without the required approved/paid financial state; completion must honor checklist and customer-review rules; cancellations must consistently remove or hide financial artifacts and release undeducted inventory reservations.
- Check technician schedule conflicts when assigning or rescheduling. Compare relevant active jobs and the intended time window, and exclude cancelled/archived work as the business rules require. Re-check inside the write boundary so concurrent requests cannot double-book a technician.
- Inventory quantities and requested usage must be positive where appropriate, and stock must never become negative. Validate availability and update stock, `JobInventoryUsage`, and `StockMovement` together in one transaction. Account for concurrent updates; a stale pre-check followed by `SaveChangesAsync` is not enough protection.
- Every stock change must retain an audit movement with the item, signed quantity, actor, timestamp, reason/source, and related request where applicable. Do not silently edit inventory totals.
- Compute quotation and invoice totals on the server from validated labor/line items and current authorized inventory pricing. Never trust browser-submitted totals, prices, breakdowns, payment state, or ownership IDs.
- Payment processing must be idempotent. Reject or safely return success for repeat payment callbacks/submissions, prevent duplicate or over-payments, validate amount/currency/reference, and transition a payable invoice only once. The current app has no external payment-provider integration, so do not imply that a local `Paid` flag proves funds were captured.
- Use a database transaction for multi-record financial, inventory, cancellation, assignment, and account/role operations. Commit only after all validation and writes succeed; roll back the whole operation on failure.

## Security requirements

- Never add, copy, log, screenshot, or commit credentials, connection strings, API keys, cookies, tokens, user secrets, or production customer data. Treat existing configuration values as sensitive even if a file is tracked.
- Prefer environment variables, ASP.NET Core user secrets, or ignored `appsettings.Development.json` for local secrets. Keep checked-in configuration limited to safe defaults/placeholders. Do not print configuration values during diagnostics.
- Preserve Identity password, lockout, cookie, and session behavior unless the task explicitly changes authentication. Use `UserManager`, `SignInManager`, and role APIs rather than manipulating Identity tables directly.
- Apply antiforgery validation to cookie-authenticated state changes. API endpoints need an intentional authentication/CSRF model; do not assume `[ApiController]` makes cookie-authenticated writes safe.
- Prevent overposting with explicit input DTOs/ViewModels and allowlisted assignments. Re-fetch the target entity and set only fields the caller is authorized to change.
- Prevent IDOR by scoping every lookup by both resource ID and current customer ownership, technician assignment, or administrator permission before returning even metadata.
- Keep Razor's output encoding intact. Safely serialize values passed to JavaScript and do not render untrusted HTML.
- For uploads, enforce server-side size limits, approved types based on content as well as extension, randomized server filenames, a fixed safe storage root, and non-executable serving. Prevent traversal and do not expose physical paths. Remove files only when ownership and lifecycle are clear.
- In SignalR, authorize group joins and every read/write/broadcast, not just the initial connection. Never trust a caller-provided group/request ID, sender ID, role, or display name.
- Avoid placing sensitive content in logs. Log enough context for diagnosis and audit without passwords, tokens, connection strings, payment secrets, or unnecessary personal data.

## Verification and debugging

`HomeServeIT.Web.Tests` contains xUnit regression tests. Its fast transaction tests use an in-memory SQLite database. Provider-specific race tests create and delete a uniquely named MySQL database only when `HOMESERVE_TEST_CONNECTION` is supplied; they skip otherwise. Point that variable only at a local disposable MySQL server account allowed to create and delete test databases. Never reuse a shared, staging, or production connection.

```bash
dotnet test HomeServeIT.slnx --no-restore
# After exporting HOMESERVE_TEST_CONNECTION from a secret store:
dotnet test HomeServeIT.Web.Tests --no-restore --filter FullyQualifiedName~MySqlConcurrencyTests
```

The `ScreenshotBot` npm `test` script remains a placeholder and is not evidence. Automated tests cover only their named cases; continue with focused runtime/manual checks proportional to each change.

For bug fixes and user-visible changes:

1. Read the relevant request path end to end: route, authorization, controller/hub, service, EF query/write, ViewModel, Razor/JavaScript, and generated request.
2. Reproduce the issue before changing code when the environment permits. Record the role, resource ownership, starting data state, route, and observed failure.
3. Before starting the app, verify that its connection targets a safe local database. Development startup calls `Database.MigrateAsync`; non-Development deployment uses the reviewed explicit `--initialize-database` path. Never enable disposable fixture/reset options against ordinary application data.
4. Run the actual application with the `http` launch profile. Keep server output visible and inspect exceptions, warnings, failed queries, and status codes.
5. When browser tooling is available, open `http://localhost:5160`, exercise the affected workflow, and inspect the browser console and network panel for JavaScript errors, failed requests, redirects, antiforgery failures, and unexpected payloads.
6. Test authorization from the relevant roles and include a negative ownership/assignment case for IDOR-sensitive work. For stateful workflows, test invalid transitions, retries, and duplicate submissions.
7. Verify the fix through the running app, then rebuild. Report exactly what was checked and any checks not possible because of database, browser, account, or environment limitations.

For CSS/view changes, ensure Tailwind regeneration succeeds and inspect the affected desktop and responsive layout. For SignalR changes, verify connection, authorized group join, persistence, broadcast, reconnect behavior, and rejection of unauthorized request IDs. For EF/multi-write changes, verify success and rollback paths and inspect the resulting related rows and audit records.
